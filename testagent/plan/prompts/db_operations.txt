## 决策原则

1. **只在真正需要时才操作数据库**：不是所有测试用例都需要 DB 操作。只有涉及数据创建、数据验证、数据清理的场景才需要。
2. **setup 阶段**：如果测试需要特定的数据库前置数据（如测试用户、测试订单），在 setup 阶段创建。
3. **verify 阶段**：如果测试步骤应该产生数据库变更（如注册用户、提交订单），在 verify 阶段查询验证。如果 setup 阶段创建了测试数据，在 verify 阶段清理。
4. **参数化查询**：使用 `:param_name` 占位符，不要拼接 SQL 字符串。
5. **安全第一**：只生成安全的 SQL 操作，不要 DROP/ALTER/TRUNCATE。

## 输出 JSON Schema

只输出一个合法的 JSON 对象，不要其他任何文字。

```json
{{
  "needs_db": true/false,
  "reasoning": "一句话说明为什么需要/不需要 DB 操作",
  "operations": [
    {{
      "op": "query",
      "description": "查询测试用户是否存在",
      "sql": "SELECT * FROM users WHERE username = :username",
      "params": {{"username": "test_user_001"}}
    }}
  ]
}}
```

### op 取值

| op | 含义 | 适用场景 |
|---|---|---|
| `inspect` | 查看表结构 | 不确定表结构时 |
| `query` | SELECT 查询 | 验证数据、检查前置条件 |
| `execute` | 写操作（INSERT/UPDATE/DELETE） | 创建测试数据、修改数据 |
| `cleanup` | 清理本会话测试数据 | verify 阶段清理 setup 创建的数据 |

### 字段说明

- `needs_db`：是否需要 DB 操作。不需要时 operations 为空数组。
- `reasoning`：简要说明决策依据。
- `operations`：要执行的操作列表，按执行顺序排列。
- `op`：操作类型（inspect/query/execute/cleanup）。
- `description`：操作的中文描述，用于日志输出。
- `sql`：SQL 语句（inspect 和 cleanup 不需要 sql 字段）。
- `params`：SQL 参数（inspect 和 cleanup 不需要 params 字段）。

## 重要约束

- **不要假设表结构**：参考上面的 Database Schema 信息来生成 SQL。
- **cleanup 操作**：如果 setup 阶段用 `execute` 创建了数据，verify 阶段应该用 `cleanup` 来清理（而不是手写 DELETE）。cleanup 操作不需要 sql 和 params。
- **不要过度操作**：如果测试用例与数据库无关（如纯 UI 交互），设置 `needs_db: false`。
