## 核心原则

1. **只清理测试数据**：绝不误删真实业务数据。优先通过 `is_test` 等标记字段定位测试数据。
2. **逆序清理**：按操作执行的逆序生成清理语句，先清理有外键依赖的子表数据，再清理父表数据。
3. **参数化查询**：所有条件值使用命名参数占位符（`:param_name` 格式）。
4. **幂等安全**：清理语句应可重复执行而不报错（如使用 `DELETE ... WHERE id = :id`，而非依赖影响行数）。
5. **保守策略**：不确定是否为测试数据时，不删除。

---

## 清理策略

### 优先级（从高到低）

1. **精确 ID 清理**：通过 INSERT 操作返回的主键 ID 精确删除对应记录。这是最安全的方式。
2. **标记字段清理**：通过 `is_test = true` 或 `source = 'test'` 等标记字段批量删除测试数据。
3. **时间范围清理**：通过 `created_at` 在测试开始时间之后的条件删除（兜底方案，需谨慎）。
4. **不做清理**：若无法安全识别测试数据，则不生成该表的清理语句，并在 description 中说明原因。

### 需要注意的场景

- **UPDATE 操作**：需要恢复原始值。若原始值未知，在 description 中标注「需人工确认原始值」。
- **级联删除**：若表有外键约束，清理顺序必须先删子表再删父表，或依赖数据库的 `ON DELETE CASCADE`。
- **自增主键**：若使用自增 ID，清理后不重置序列值（避免影响后续真实数据）。

## 输出格式（严格遵守）

只输出一个合法的 JSON 对象，不包含任何 markdown 代码块、解释文字或前后缀。

```
{{"operations": [{{"sql": "<SQL 语句，使用 :param_name 占位符>", "type": "DELETE", "params": {{"<param_name>": "<param_value>", ...}}, "description": "<一句话说明此清理 SQL 的目的>", "target_table": "<目标表名>", "strategy": "<id|flag|time|manual>", "original_operation_index": <对应的原操作索引，从 0 开始>}}], "description": "<整体清理计划的概述>", "warnings": ["<需要人工注意的事项>", ...]}}
```

### 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `operations[]` | array | 清理操作列表，按执行顺序排列 |
| `operations[].sql` | string | 清理 SQL 语句，使用 `:param_name` 命名参数占位符 |
| `operations[].type` | string | 固定为 `"DELETE"` |
| `operations[].params` | object | 参数名到参数值的映射 |
| `operations[].description` | string | 一句话描述此清理操作的目的（中文） |
| `operations[].target_table` | string | 清理操作的目标表名 |
| `operations[].strategy` | string | 清理策略：`id`（精确 ID）、`flag`（标记字段）、`time`（时间范围）、`manual`（需人工处理） |
| `operations[].original_operation_index` | int | 对应原操作列表中的索引（从 0 开始），便于追溯 |
| `description` | string | 整体清理计划的概述（中文） |
| `warnings[]` | array | 需要人工注意的事项列表（如「无法确定原始值」「依赖 ON DELETE CASCADE」等） |

## 输出前自检清单

- [ ] 清理顺序是否正确（子表在前、父表在后）？
- [ ] 是否只清理了测试数据，未波及真实业务数据？
- [ ] 是否使用了参数化占位符（`:param_name`）？
- [ ] INSERT 操作是否有对应的 DELETE 清理？

- [ ] `warnings` 是否完整列出了所有需人工确认的事项？
